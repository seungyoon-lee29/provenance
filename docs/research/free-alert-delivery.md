# 무료 알림 전달과 운영 이메일 경로

- 조사 기준일: 2026-07-14
- 예산: 외부 알림 공급자 구독비 `USD 0/월`
- 목표: 인앱, Web Push와 저용량 운영 이메일을 가짜 성공 상태 없이 검증한다.

## 결정

MVP의 정본은 로그인 User Workspace의 **인앱 Notification Record**다. Alert Rule의 전이가 감지되면 rule state, 정확히 한 개의 `Alert Occurrence`와 Notification Record를 같은 transaction에 저장한 뒤에만 외부 전달을 평가한다. 동의·설정·권리·만료 검사를 통과한 채널에만 Delivery Intent를 만든다. 미설정·미동의 채널에는 Intent나 외부 outbox 작업을 만들지 않고, Notification Record에 채널 평가 결과를 남긴다. `Alert Channel Availability`는 deployment provider readiness, workspace consent/verified address, 현재 device/install의 permission/subscription과 category quota/circuit을 별도 축으로 저장하고 요청 시 합성해 UI의 `설정 필요`를 구동한다. 브라우저가 오프라인이거나 Web Push·이메일이 실패·해지돼도 인앱 기록은 사라지지 않는다.

| 채널 | MVP 상태 | 비용과 전제 | 전달 보장 |
| --- | --- | --- | --- |
| 인앱 inbox | 필수, 기본 활성 | 자체 PostgreSQL·worker | durable source of truth |
| 표준 Web Push | 선택, 명시적 opt-in | HTTPS, service worker, 앱 소유 VAPID key; 별도 유료 SaaS 없음 | best effort; push service accepted를 delivered로 부르지 않음 |
| Resend email | 선택, 명시적 opt-in | Free `USD 0`, 소유 domain과 DNS 검증 필요 | best effort; webhook 사실만 기록 |
| Mailpit email | local/CI 전용 | Docker SMTP `1025`, UI/API `8025` | 외부 발송하지 않는 test capture |
| SMS·메신저·마케팅 메일 | 보류 | 현재 무료·권리·운영 경로 밖 | 없음 |

Resend Free는 현재 transactional email 100건/일, 3,000건/월, custom domain 1개를 제공한다. 송·수신과 수신자별 사용량이 quota에 포함되며 무료 overage는 없다. 이 값은 release 직전 공식 문서와 runtime header로 다시 확인한다. [Resend quota](https://resend.com/docs/knowledge-base/account-quotas-and-limits), [Resend 가격](https://resend.com/pricing/), [domain 검증](https://resend.com/docs/dashboard/domains/introduction)

## 도메인 모델과 상태

- `Alert Rule`: 사용자가 만든 조건과 source/freshness 요구, cooldown, channel, TTL을 가진다. 가격 rule은 false→true 전이에서만 발화하고 조건이 다시 풀린 뒤 re-arm한다.
- `Alert Occurrence`: `(workspaceId, ruleId, conditionRevision, transitionSequence)`가 unique인 발화 사실이다. rule watermark, occurrence와 Notification Record를 같은 transaction에 쓰므로 poll 재실행·worker crash·늦게 도착한 관측이 중복 알림을 만들지 않는다.
- `Account Security Event`: 이메일 확인, magic link, 로그인·credential 변경처럼 Alert Rule과 무관한 안정적 원인이다. 익명 요청도 request identity·purpose·request security epoch·expiry로 중복 제거하고 가짜 Alert Occurrence를 만들지 않는다. 인증된 workspace 사건은 정책에 따라 인앱 Notification Record도 만들지만 익명 확인·복구 요청은 email Intent만 만들 수 있다.
- `Delivery Cause`: `AlertOccurrence | AccountSecurityEvent`의 tagged identity다. 모든 외부 delivery는 한 cause를 가져야 한다.
- `Notification Record`: `workspaceId`, origin (`AlertOccurrence | AccountSecurityEvent`), category, optional related source-owned reference, trigger/as-of time, safe internal route, read/dismiss 상태를 가진 durable 인앱 기록이다. 기본 보존은 365일이며 원천 License Scope가 더 짧으면 그 기간이 우선한다.
- `Workspace Channel Endpoint Reference`: `WorkspaceFinancialEmailEndpoint | WorkspaceSecurityEmailEndpoint | WorkspaceWebPushEndpoint` purpose-tagged 암호화 reference다. financial variant는 workspace membership·financial-consent epoch·verified-address revision, security variant는 membership/account-state·security-notice epoch·verified-address revision, Web Push variant는 device-binding auth epoch·consent version을 사용한다. financial opt-out은 security variant를 비활성화하지 않는다. raw endpoint나 email address를 다른 aggregate에 복사하지 않는다.
- `Pending Account Email Target`: 아직 workspace/verified address가 없는 확인·복구 요청에서 Account Security Event, pending identity, purpose, request security epoch와 expiry에 묶인 짧은 수명의 암호화 reference다. financial alert에는 사용할 수 없다.
- `Delivery Action Material Reference`: 비동기 email renderer가 쓰는 원문 secret을 hash-only verifier와 별도로 envelope vault에 암호화한 `AccountChallengeMaterial | UnsubscribeMaterial` 참조다. account variant는 Account Security Event·purpose·request/auth epoch·expiry, unsubscribe variant는 workspace·endpoint·topic·consent lineage·Delivery Intent에 묶는다. 허용된 renderer만 해석하고 provider 수락·확정 실패·expiry 뒤 원문 material을 삭제한다.
- `Delivery Target Reference`: `WorkspaceFinancialEmailEndpoint | WorkspaceSecurityEmailEndpoint | WorkspaceWebPushEndpoint | PendingAccountEmailTarget`의 tagged union이다. cause·purpose/target 조합을 dispatch에서 검증한다.
- `Delivery Intent`: `(causeId, channel, destinationFingerprint)` unique key와 Delivery Target Reference를 가진 outbox 작업이다. `sourceReference?: SourceOwnedReference`와 `deliveryActionMaterialReference?: DeliveryActionMaterialReference`는 택일 union이 아니라 독립 필드다. financial email은 source reference, `UnsubscribeMaterial` reference와 WorkspaceFinancialEmailEndpoint가 모두 필수이고, financial Web Push는 source reference와 WorkspaceWebPushEndpoint만 허용하며, MVP account challenge email은 source reference 없이 `AccountChallengeMaterial` reference와 PendingAccountEmailTarget이 필수다. allowlisted 로그인·credential 변경 `authenticated_security_notice`는 `AccountSecurityEvent + email + WorkspaceSecurityEmailEndpoint`일 때만 source와 action material 없이 허용한다. 다른 누락·variant·purpose·target 조합은 Intent 생성 전에 거절한다. expiry·rights/consent snapshot, 최초 `templateRevision`과 payload hash는 immutable 속성일 뿐 unique identity를 바꾸지 않는다. 같은 원인에 새 template을 배포해도 두 번째 Intent를 만들지 않으며 새 메시지가 필요하면 새 cause가 필요하다.
- `Delivery Fact`: immutable append-only 사실이다. `queued`, `provider_accepted`, `delayed`, `delivered`, `seen`, `bounced`, `complained`, `provider_suppressed`, `suppressed`, `failed`, `expired`와 reason, provider event time을 보존하며 단일 상태를 되돌리지 않는다.

destination fingerprint는 환경별 안정적인 keyed HMAC key와 key version을 함께 저장한다. 회전은 old/new dual lookup과 transactional backfill을 마친 뒤 old key를 폐기하며 회전 중 같은 cause/endpoint replay가 기존 unique identity를 우회하지 못해야 한다.

HTTP 2xx와 Resend `email.sent`는 모두 provider가 요청을 받아들였다는 `provider_accepted` 증거일 뿐 별도 `sent` 단계나 최종 전달 보장이 아니다. `email.delivered`만 수신 메일 서버 수락을 뜻한다. open/click tracking은 비활성이고 webhook open/click도 `seen`으로 쓰지 않는다. `seen`은 foreground client가 현재 Viewer Context, workspace와 auth epoch로 Notification Record 렌더링을 승인한 뒤 보내는 acknowledgement만 기록한다. notification click 자체도 seen 근거가 아니다.

Webhook ingress는 edge에서 POST와 `application/json`, header 64개/16 KiB, raw body 256 KiB, 2초 read deadline을 body buffering 전에 강제한다. trusted peer/IP bucket 10 requests/second burst 50과 전역 50 requests/second burst 100을 적용하고 초과에는 `Retry-After`가 있는 429를 반환한다. raw body의 서명과 `svix-timestamp` clock skew를 검증한 뒤 파싱한다.

검증된 event의 provider message id를 domain-separated `ERASURE_TOMBSTONE_HMAC` active key와 아직 유효한 모든 previous key로 계산해 deletion ledger/Processor Erasure tombstone을 먼저 조회한다. 일치하면 raw body·recipient를 durable 저장하지 않고 비식별 `dropped_after_erasure` counter만 증가시킨다. 그 밖의 event는 `(provider, environment, svix-id)` unique인 durable webhook inbox에 원자적으로 저장한 뒤 2xx를 반환한다. worker는 서버가 원래 Intent에 저장한 provider message id로 `WorkspaceId | PendingIdentityId` owner, recipient fingerprint와 template revision을 찾고, API acknowledgement보다 webhook이 먼저 오면 unbound 상태로 재시도한다. webhook metadata가 주장하는 owner/address는 신뢰하지 않는다. Fact commit과 inbox `processed` 전이는 같은 transaction이며 crash 뒤 재전달도 Fact를 잃지 않는다. event `created_at`은 ordering과 보존 계산에만 쓰고 replay 거절 기준으로 쓰지 않으므로 오래된 event도 fresh valid Svix signature로 수동 replay할 수 있다. versioned secret rotation window를 검증하고 owner 또는 recipient/template 불일치는 격리한다. 일정 기간 bind되지 않은 event는 삭제가 아니라 운영 경고와 격리 상태가 된다. [Resend webhook](https://resend.com/docs/webhooks/introduction), [event types](https://resend.com/docs/webhooks/event-types)

## 외부 전달 권리

financial alert Intent는 원문을 복사하지 않고 source-owned reference와 목적별 rights snapshot/version만 보존한다. `web_push` 또는 `email_provider`로 보낼 때 template rendering 직전과 실제 dispatch 직전에 financial email은 Delivery Authorization Context, Web Push는 device-bound delivery context로 License Scope의 외부 전달·파생물 권리를 원천 소유 모듈에서 다시 해석한다. email Intent 생성 transaction은 unsubscribe token hash와 consent-lineage-bound `DeliveryActionMaterialReference<UnsubscribeMaterial>`도 함께 저장한다. renderer는 provider accepted 전 retry에서 같은 원문과 payload hash를 재사용하고 accepted·확정 실패·expiry 뒤 암호화 원문만 삭제한다. 허용되면 최소화된 template만 만들고, 거절되면 공개 가능한 일반 메타데이터와 opaque Notification ID만 보내거나 `suppressed/license_restricted`를 남긴다. 제한된 가격·포트폴리오·기사·공시 내용은 권리 판정 전에 payload, subject 또는 외부 provider log에 넣지 않는다.

security/account Intent는 Evidence나 financial License Scope를 가장하지 않는다. Account Security Event의 purpose policy, pending identity 또는 workspace/auth epoch, request abuse decision, Delivery Target Reference와 template allowlist를 render와 dispatch 직전에 다시 검증한다. account challenge purpose는 `DeliveryActionMaterialReference<AccountChallengeMaterial>`도 필수이고 action material resolver는 원문 token/code를 account renderer에만 주며 log·metadata에는 주지 않는다. allowlisted `authenticated_security_notice` purpose는 Identity가 발급한 SecurityNoticeDeliveryContext로 event purpose/expiry, workspace membership/account active, security-notice epoch, verified-address revision과 deletion fence를 render·dispatch 직전에 다시 확인하고 WorkspaceSecurityEmailEndpoint에만 source/action material 없이 보낼 수 있다. financial consent와 보통 logout은 이 context를 폐기하지 않지만 address/security revision 변경은 폐기한다. `PendingAccountEmailTarget`은 email 확인·복구 challenge에만 허용하고 Web Push·financial alert·authenticated notice와 조합하면 호출 없이 거절한다.

## 동의와 해지

- `security_account`: 이메일 확인, magic link, 로그인·credential 변경 같은 계정 보안 메일이다. alert topic 해지와 분리하고 마케팅에 사용하지 않는다.
- `financial_alert`: 가격·뉴스·공시·포트폴리오 alert다. 이메일과 Web Push는 채널별 unchecked opt-in이 기본이고 동의 시각·출처·정책 버전을 저장한다.
- `marketing`: MVP에서는 adapter와 UI를 등록하지 않는다.

Web Push permission은 initial load, login이나 route 이동에서 요청하지 않는다. 사용자가 `브라우저 알림 켜기`를 직접 누른 뒤에만 설명 화면을 거쳐 요청한다. `denied`면 반복 prompt를 하지 않고 브라우저 설정 안내와 인앱-only 상태를 보여준다. Web Push worker는 실제 전송 직전에 device binding auth epoch, consent, endpoint와 expiry를 다시 확인한다. financial email worker는 FinancialEmailDeliveryContext의 workspace membership, consent epoch, verified-address revision과 expiry를 확인하며 logout만으로 억제하지 않는다. authenticated security notice worker는 SecurityNoticeDeliveryContext의 event purpose/expiry, account state, security-notice epoch, address revision과 deletion fence를 확인하고 financial opt-out과 보통 logout에는 영향받지 않는다. Pending account email은 Account Security Event purpose, request security epoch, target과 token expiry만 확인한다. [Notifications permission](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)

financial alert email에는 preferences link와 RFC 8058 `List-Unsubscribe`/`List-Unsubscribe-Post`를 넣는다. unsubscribe token은 256-bit 이상의 CSPRNG 값이고 DB에는 hash만 저장한다. workspace, endpoint, topic, channel과 연속된 opt-in `consentLineageId`에 바인딩하며 calendar expiry를 두지 않고 해당 lineage가 활성인 동안 모든 과거 발송 token이 현재 opt-in을 해지할 수 있어야 한다. 명시적 opt-out 뒤 consumed hash는 30일 더 보존해 반복 POST를 idempotent하게 처리하고, 이후 명시적 re-opt-in은 새 lineage를 만들어 이전 token이 새 동의를 바꾸지 못하게 한다. 비교는 constant-time이다. 최초 유효 POST는 opt-out을 기록한다. 같은 token·같은 lineage의 반복 POST는 추가 부작용 없이 같은 일반 `200/202`를 반환하고 opt-out을 유지한다. 변조되거나 다른 workspace/topic/channel/lineage에 쓰인 token은 상태를 바꾸지 않고 enumeration을 막는 동일한 일반 응답을 반환하되 내부 invalid audit만 남긴다. GET은 해지하지 않는 확인 화면만 제공한다. 두 응답은 redirect 없이 `Cache-Control: no-store`와 `Referrer-Policy: no-referrer`를 쓰고 URL·access log·analytics에 token을 남기지 않는다. [Resend unsubscribe](https://resend.com/docs/dashboard/emails/add-unsubscribe-to-transactional-emails), [RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html)

unsubscribe ingress는 GET/POST 외 method를 거절한다. POST는 `application/x-www-form-urlencoded`와 `multipart/form-data`만 받고 body 8 KiB, URL 4 KiB, header 64개/16 KiB와 2초 read deadline을 buffering 전에 강제한다. urlencoded body는 정확히 한 개의 `List-Unsubscribe=One-Click` pair만 허용하고, multipart도 같은 이름·값의 text part 하나만 허용하며 file, 추가·중복 field, nested multipart와 잘못된 boundary는 거절한다. IP prefix 10회/분·100회/일과 전역 50회/초 bucket을 적용한다. invalid audit은 token 또는 token fingerprint를 durable key로 쓰지 않는다. allowlisted `route + reason + minute + edgeRegion`의 고정-cardinality counter와 deployment 전체에서 최대 20건/시간인 redacted reservoir sample만 24시간 보존한다. unique random token flood도 `routes × reasons × regions × 1,440 + 480` durable row/24시간 상한을 넘지 않으며 sample에는 token·digest·URL이 없다.

Quiet Hours는 기본 비활성이다. 사용자가 IANA timezone, 시작·종료를 설정하면 financial email/Web Push만 보류하며 인앱 기록은 즉시 만든다. MVP에는 critical bypass가 없다. 같은 `(ruleId, instrumentId, conditionRevision)`의 occurrence는 수신 시각이 아니라 `transitionSequence` 순으로 coalesce한다. 더 늦게 관측된 오래된 occurrence가 최신 것을 덮지 않으며 교체된 Intent는 `suppressed/superseded_quiet_hours`가 된다. 종료 시 TTL이 유효한 최신 occurrence만 보내고 digest는 포함한 모든 Notification Record와 optional related source-owned reference를 보존한다. 만료 항목은 `expired_quiet_hours`로 남긴다. 계정 보안 메일은 Quiet Hours 적용 대상이 아니다.

## Web Push

production은 HTTPS와 service worker를 요구한다. `serviceWorker`, `Notification`, `PushManager`를 feature detection하고 `subscribe({ userVisibleOnly: true, applicationServerKey })`를 사용한다. iOS/iPadOS는 Home Screen web app에서 지원되므로 일반 tab에는 설치 안내와 인앱-only fallback을 제공한다. 브라우저·버전 문자열이 아니라 기능을 판정한다. [PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe), [iOS/iPadOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

- VAPID private key는 server-only이고 active public key+version만 server bootstrap endpoint로 브라우저에 제공한다. 빌드 시 `NEXT_PUBLIC_*` 값으로 고정하지 않는다. active version/public/private/subject 네 설정은 전부 있어야 하며 부분 설정은 구독 UI, Intent와 외부 호출을 모두 비활성화한다.
- workspace당 browser profile/install별 구독을 최대 5개 저장한다. endpoint, `p256dh`, `auth`, VAPID key version은 delivery keyring의 envelope key로 암호화하고 ciphertext에 key version을 기록한다. AAD는 `workspace + device/endpoint + web_push channel + device-binding auth epoch`이며 pending identity를 허용하지 않는다. 로그에는 keyed-HMAC endpoint fingerprint만 남기고 subscription은 workspace, device install, auth epoch와 VAPID key version에 함께 바인딩한다.
- 구독 endpoint는 인증된 browser의 `PushSubscription` 등록 command에서만 받고 전용 `PushTransport`가 전송한다. HTTPS, port 443, userinfo 없음, 버전이 고정된 정확한 push-service host/pattern registry를 모두 만족해야 하며 모르는 host는 거절한다. 범용 user-supplied URL fetch로 구현하지 않는다.
- `PushTransport`는 connect마다 DNS를 다시 해석하고 IPv4/IPv6의 loopback, private/RFC1918, ULA, link-local, multicast와 reserved 주소를 거절한다. redirect는 0회, 응답 body 크기와 connect/read timeout은 고정하고 production egress proxy가 같은 allowlist를 강제한다. alternate port, userinfo, redirect, DNS rebinding과 public→private multi-answer도 contract test한다.
- app open 때 `getSubscription()`을 server binding과 대조한다. logout/workspace switch는 해당 browser binding을 해제하며 다음 로그인 사용자는 다시 opt-in한다.
- VAPID signing key를 회전할 때는 versioned Secret Manager keyring의 이전 pair를 `notAfter`까지 제한적으로 유지하면서 active public key 재등록을 유도한다. `notAfter` 뒤에는 남은 subscription을 비활성화해 재-opt-in을 요구하며 compromised version은 emergency revoke로 즉시 폐기한다. 휴면 subscription 때문에 이전 private key를 무기한 보존하지 않는다. Resend webhook도 active+previous version의 제한된 rotation window를 사용한다.
- payload는 4,096 bytes 이하이고 lock screen 기본 내용은 일반화한다. opaque `notificationId`, category, allowlisted internal route, `issuedAt/expiresAt`만 담고 계좌번호, 보유 수량, P&L, 주문 세부, user id, credential, 기사 전문은 넣지 않는다.
- RFC 8030 `Topic`은 Delivery Intent에서 안정적으로 도출하고 service worker의 notification `tag`와 client-side notificationId dedupe에 같은 identity를 사용한다. accept-before-timeout 뒤 재시도돼도 사용자에게 두 개를 표시하지 않는다.
- push request에 TTL을 넣고 market/price 5분, news/filing 1시간, account/system 24시간을 기본 상한으로 둔다. 만료된 push는 보내지 않는다.
- HTTP 404/410은 subscription을 비활성화하고 재시도하지 않는다. 400/413은 payload/config 영구 실패, 401/403은 VAPID circuit breaker, 429는 `Retry-After`, network/5xx는 TTL 안에서 exponential backoff+jitter다.

Web Push는 주문 실행, kill switch, 위험 통제나 반드시 전달돼야 하는 기능에 사용하지 않는다. push service 수락과 OS 표시·사용자 열람은 서로 다른 사실이다. [Web Push protocol](https://www.rfc-editor.org/rfc/rfc8030.html), [payload encryption](https://www.rfc-editor.org/rfc/rfc8291.html), [VAPID](https://www.rfc-editor.org/rfc/rfc8292.html)

## Email과 무료 quota

운영 기본 adapter는 Resend Free다. 소유 domain의 전용 subdomain을 SPF/DKIM으로 검증하고 DMARC를 권장한다. domain이나 API key가 없으면 인앱은 정상 동작하고 이메일 capability만 `unavailable/configuration_required`다. 부분 설정은 fail closed이며 outbound call, email Delivery Intent와 가짜 `sent` 상태가 0이어야 한다. Mailpit은 development/test에서만 허용하고 staging/production 선택은 startup error다.

security/account와 financial alert는 각각 감사된 versioned template allowlist만 사용한다. subject와 preheader는 계좌·포트폴리오·P&L·포지션·주문·기사 전문·직접 식별자를 포함하지 않고 일반 문구와 opaque internal ID만 쓴다. body도 최소 정보와 `APP_PUBLIC_ORIGIN`에서 조립한 allowlisted internal deep link만 포함하며 open/click tracking을 비활성화한다. 앱의 API metadata·webhook normalization·log에는 token이나 민감 본문을 복사하지 않는다. 다만 Resend Free가 전달을 위해 email body와 token을 처리·저장할 수 있으므로 보안/개인정보 고지에 provider와 무료 plan의 보존 경계를 명시하고 financial email opt-in에 포함한다. 외부 저장 자체가 허용되지 않는 자료는 email body에 넣지 않고 인앱으로만 보여준다. [Resend message storage](https://resend.com/docs/knowledge-base/how-do-i-ensure-sensitive-data-isnt-stored-on-resend)

magic link token은 256-bit 이상의 CSPRNG 값으로 만들고 hash만 저장한다. user/pending identity, purpose, request/auth epoch와 allowlisted return route에 바인딩하고 10분 이내 만료·단일 사용으로 처리한다. GET은 scanner/prefetch가 token을 소비하지 않는 `no-store`, `no-referrer` 확인 화면만 만들고, 명시적 사용자 동작의 CSRF-protected POST가 token compare-and-consume와 session issuance를 한 transaction에서 수행한다. 동시 POST 한 개만 성공하고 사용 뒤 replay는 session을 만들지 않는다.

수동 fallback은 같은 challenge family에 속한 별도의 CSPRNG 10-character Crockford Base32 code를 쓰고 hash만 저장한다. purpose, pending identity, request/auth epoch와 expiry를 link token과 동일하게 묶고 주소/device/IP cap에 더해 family 전체 최대 5회 실패만 허용한다. 5회 실패나 만료는 link와 code를 모두 폐기하고, 어느 한 경로의 원자적 성공도 다른 경로를 동시에 소비한다. code POST도 CSRF와 enumeration-safe 응답을 적용하고 원문 code·attempt identifier를 log/analytics에 남기지 않는다. 민감한 계좌·주문 상세 화면은 별도 reauthentication을 요구한다.

무료 quota의 공식 plan limit은 100건/일·3,000건/월이다. `account/security`를 위한 최소 25건/일·750건/월은 예약분이지 최대치가 아니며, optional financial email은 전역 75건/일·2,250건/월과 사용자 5건/일·60건/월을 넘지 않는다. MVP inbound email은 비활성화한다.

quota header는 남은 수가 아니라 공급자가 특정 snapshot 시각까지 관측한 사용량일 수 있으므로 의미와 snapshot 시각을 adapter에서 typed field로 정규화한다. `effectiveUsed = providerObservedAtSnapshot + localProviderAcceptedDeltaSinceSnapshot + outstandingReservations`로 계산하고 inbound는 비활성이라 0이다. local accepted가 provider snapshot에 이미 포함된 구간을 다시 더하지 않는다. day/month 각각 `securityReserveRemaining = max(0, securityMinimum - securityAcceptedOrReserved)`를 구하고 optional 가용량은 `max(0, min(optionalPlanCap - optionalAcceptedOrReserved, planLimit - effectiveUsed - securityReserveRemaining))`이다. 분류할 수 없는 provider 사용량도 effectiveUsed에 포함하므로 security reserve를 침범하지 않는다. outbox lease와 quota reservation을 한 transaction에서 원자적으로 잡고, 확실한 pre-accept 실패만 예약을 반납한다. provider 수락 또는 timeout으로 수락 여부가 불명확하면 예약을 유지해 webhook/header reconciliation으로 정산한다. quota 소진 시 유료 overage나 다른 provider로 자동 전환하지 않고 optional email을 `suppressed/quota`로 남기며 인앱은 유지한다.

account email abuse limit은 정규화 주소의 keyed HMAC 기준 5건/15분·20건/일, device/session 10건/15분·30건/일, IP prefix 30건/15분·100건/일을 모두 적용한다. account/security 최소 예약 25건/일은 미검증 익명 요청 10건, self-hosted proof/risk check를 통과한 가입·기존-account recovery 10건, authenticated security notice 5건의 보호 budget으로 나눈다. 미검증 budget이 소진돼도 proof를 통과한 정상 요청은 별도 protected recovery budget과 주소/device/IP cap을 통과해 전달할 수 있고, 한 bucket의 미사용분을 공격자가 다른 bucket에서 빌려 쓰지 못한다. 모든 protected budget이 소진된 경우에만 enumeration-safe 응답과 지원 경로를 제공한다. 비로그인 요청은 허용·제한·미등록 주소에 같은 status/body/timing class와 `요청이 처리되었습니다` 같은 비전달 보장 문구를 반환해 account enumeration을 막고, 인증된 사용자의 설정 화면에만 안전한 재시도 시각을 표시한다.

각 email은 DB unique key와 동일 payload의 Resend `Idempotency-Key`를 함께 사용한다. provider idempotency 보존 24시간은 network retry 보호일 뿐 장기 중복 제거 정본은 DB다. timeout/network/5xx만 같은 key·payload로 재시도한다. 429는 adapter가 request-rate, daily quota, monthly quota로 분류한다. request-rate는 `Retry-After` 안에서 재시도하고 daily quota는 Intent TTL이 다음 reset까지 유효할 때만 대기하며 monthly quota는 억제·만료한다. 401/403은 provider circuit을 열고 400/422와 invalid recipient/domain/config는 영구 실패다. API 2xx 뒤에는 다시 submit하지 않고 webhook의 delayed/delivered/bounced/complained/failed/provider-suppressed를 기다린다. [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [webhook signature](https://resend.com/docs/webhooks/verify-webhooks-requests)

hard bounce는 address를 전달 불가로 만들고 수정·재검증 전까지 모든 메일을 중지한다. complaint는 optional alert opt-out과 address suppression으로 처리한다. Resend suppression을 자동 해제하지 않는다. 품질 지표는 최근 7일 rolling window와 provider-accepted external email을 분모로 계산한다. 표본 200건 이상에서 bounce 3% 또는 complaint 0.05%면 optional email circuit을 열고, 200건 미만에서는 complaint 한 건도 경고와 수동 검토를 만들되 비율만으로 자동 차단하지 않는다. 수동 승인 또는 24시간 뒤 half-open probe를 거쳐 복구하고 이유와 reset을 감사한다. provider 제한인 bounce 4% 미만, spam 0.08% 미만보다 먼저 동작한다. [Resend suppression](https://resend.com/docs/dashboard/emails/email-suppressions), [quota와 품질 제한](https://resend.com/docs/knowledge-base/account-quotas-and-limits)

로컬과 CI는 official Mailpit `v1.30.0` image를 고정하고 docker-compose lock을 만들 때 image digest도 pin한다. `latest`나 이동하는 `stable` tag를 사용하지 않는다. app container는 `mailpit:1025`로 전송하고 내부 API는 `MAILPIT_API_BASE_URL=http://mailpit:8025`, 사람이 여는 UI는 필요할 때만 `MAILPIT_UI_URL=http://127.0.0.1:8025`로 노출한다. relay/forwarding은 비활성화하고 Mailpit API로 recipient, subject, text/html, 상태 배지, preferences URL과 retry 중복 0건을 검증한다. [Mailpit Docker](https://mailpit.axllent.org/docs/install/docker/), [Mailpit integration](https://mailpit.axllent.org/docs/integration/)

## 보존과 삭제

- Notification Record와 optional related source-owned reference는 기본 365일 보존하되 원천 권리의 더 짧은 기간이 우선한다. reference가 없는 Account Security Event record도 허용한다.
- 정규화 Delivery Fact와 webhook audit은 90일, 암호화 raw webhook body는 30일 보존한다. raw body는 서명 검증과 분쟁 분석 외에는 읽지 않는다.
- WorkspaceFinancialEmailEndpoint는 financial consent lineage 종료, WorkspaceSecurityEmailEndpoint는 address/security revision 변경 또는 account 종료, WorkspaceWebPushEndpoint는 사용자가 해지하거나 device binding이 만료될 때 비활성화한다. administrative deletion은 모든 variant를 즉시 fence한다.
- 익명 Account Security Event의 actor context allowlist는 purpose, request security epoch, risk decision, 주소/device/IP-prefix의 purpose별 keyed pseudonym뿐이다. raw IP, 전체 user-agent, 원문 email을 cause에 넣지 않는다. PendingAccountEmailTarget 원문 암호문은 terminal delivery 또는 token 만료 후 24시간 안에 삭제하고, 식별 가능한 event·abuse key는 30일 뒤 제거한다. 개인과 연결되지 않는 일/월 abuse aggregate만 최대 90일 보존한다. 미가입 주소도 소유 확인된 DSAR로 target/event/rate key 삭제를 요청할 수 있다.
- workspace/account 삭제는 즉시 logical delete와 queue dispatch fence를 세우고 Alert Rule·rule watermark/state·Alert Occurrence·Account Security Event, Notification Record·channel evaluation, Delivery Intent/Fact, WorkspaceChannelEndpoint·PendingAccountEmailTarget·DeliveryActionMaterial, webhook inbox, unsubscribe/magic-link token hash, per-user abuse/quota key와 personalized cache 접근권을 취소·삭제한다. 필요한 전역 quota 숫자는 개인·workspace와 연결할 수 없는 aggregate만 남긴다. fence 뒤 action-material resolve나 challenge session issuance는 0이어야 한다. 백업은 최대 30일 내 소거되며 restore 시 deletion ledger가 재삭제를 강제한다. 감사에는 개인을 재식별할 수 없는 최소 tombstone만 남긴다.

Resend 같은 processor의 저장은 로컬 삭제와 별도다. account 삭제 또는 DSAR가 들어오면 provider message id와 최소 암호화 target reference만 가진 `Processor Erasure Intent`를 만들고, provider가 지원하는 삭제 API 또는 support/DPA 절차로 요청해 `requested | confirmed | unavailable_until_provider_expiry | legal_exception`을 감사한다. tombstone은 raw provider id를 보존하지 않고 `(provider, environment, hmacKeyVersion, digest)`만 저장하며 HMAC 입력에는 고정 namespace `ERASURE_TOMBSTONE_HMAC`을 domain separator로 넣는다. 각 HMAC key version은 그 key로 만든 마지막 tombstone의 callback·backup 최장 TTL이 끝날 때까지 read-only로 유지하고, lookup은 active와 아직 유효한 모든 previous version을 사용한다. 따라서 raw id가 없어 재해시할 수 없는 tombstone을 key rotation으로 무력화하지 않는다. 필요한 previous key가 손실·조기 revoke된 동안에는 webhook raw durable storage를 fail closed하고 운영 경고를 내며, 새 key로 없던 것으로 간주하지 않는다. 이 nonidentifying deletion tombstone은 provider callback·backup 보존 상한보다 길게 유지해 late webhook과 restore가 개인정보를 다시 적재하지 못하게 한다. 로컬 삭제는 이 요청을 기다리지 않는다. Resend Free에서는 per-message 즉시 삭제를 보장할 수 없고 현재 기본 보존 기간 내 provider expiry에 의존할 수 있음을 사용자 고지와 삭제 응답에 밝힌다. 즉시 검증 가능한 processor 삭제가 필요한 category/content는 Resend Intent를 만들지 않고 인앱-only로 제한한다. [Resend message storage](https://resend.com/docs/knowledge-base/how-do-i-ensure-sensitive-data-isnt-stored-on-resend), [Resend DPA](https://resend.com/legal/dpa)

## Rate limit과 재시도

- 인앱 cap은 workspace의 Alert Occurrence를 세어 60건/시간·300건/일 뒤 같은 rule/instrument를 digest로 합친다. 각 occurrence의 audit 근거는 보존하고 화면에서만 합친다.
- Web Push workspace cap도 Alert Occurrence 기준 5건/5분·20건/시간·100건/일이다. 전역 cap은 실제 destination request 기준 10건/초·1,000건/일이며 endpoint 5개면 5건으로 센다. 두 cap 중 하나를 넘으면 `suppressed/rate_limit`로 인앱에 남긴다.
- financial email: 같은 rule/instrument는 30분 cooldown, 위 무료 quota cap을 함께 적용한다.
- Resend outbound는 전역 Redis token bucket을 보수적인 5 requests/second로 시작하고 공식 rate-limit header가 더 낮으면 동적으로 낮춘다. daily/monthly quota ledger와 request-rate bucket을 같은 숫자로 취급하지 않는다.
- financial external retry: 즉시, 30초, 2분, 10분, 30분, 90분의 최대 6회이며 event TTL 또는 2시간 중 이른 시각에서 종료한다.
- account email retry: 즉시, 5초, 30초, 2분, 10분, 30분, 2시간, 6시간의 최대 8회이며 action token 만료 또는 24시간 중 이른 시각에서 종료한다.

worker crash 뒤에도 stable Delivery Intent와 idempotency key로 재개한다. provider가 수락했는지 불확실하면 동일 key와 payload만 재시도하고 새 메일을 만들지 않는다. 모든 retry는 공통 provider circuit·TTL에 더해 목적별 경계를 다시 통과한다. financial email은 FinancialEmailDeliveryContext·License Scope, Web Push는 device binding auth epoch·consent·License Scope, pending account email은 purpose·request security epoch·target/token expiry, authenticated security notice는 SecurityNoticeDeliveryContext의 purpose/expiry·account state·security-notice epoch·address revision·deletion fence를 사용한다.

## 합격 기준

1. 같은 poll·transition을 동시에 100회 처리해도 rule watermark, Alert Occurrence와 Notification Record가 정확히 한 개 생긴다. transaction commit 전에는 Delivery Intent와 외부 호출이 0이다.
2. eligible channel만 idempotent Intent를 만든다. 미설정·미동의·권리 제한 채널은 channel evaluation만 남기고 Intent와 외부 호출이 0이며, 모든 경우 reload 후 인앱 기록이 보인다.
3. 다른 User Workspace의 record, endpoint, address 또는 deep link로 읽기·전달할 수 없다. logout 뒤 financial email은 유효한 FinancialEmailDeliveryContext로 지속되지만 consent/address/membership 변경에는 억제되고, Web Push와 pending account email은 각각 device-binding/request-security epoch만 사용한다. authenticated security notice는 financial opt-out·보통 logout과 독립적으로 유효하지만 address/security revision 변경, account 종료와 deletion fence에는 억제된다. unsubscribe/workspace 삭제 race는 dispatch fence와 직전 재검사로 차단한다.
4. unsupported, permission `default/denied/granted`, iOS non-Home-Screen과 workspace switch를 browser test한다. 최초 화면에는 native permission prompt가 없다.
5. PushTransport는 loopback·private·ULA·link-local·reserved address, unknown host, alternate port, userinfo, redirect와 DNS rebinding을 거절한다. allowed service의 accepted, 400, 401/403, 404, 410, 413, 429+Retry-After, accept-before-timeout과 5xx에서 retry·subscription·Topic/tag dedupe·TTL·redaction을 검증한다.
6. external-delivery 권리를 rendering과 dispatch 양쪽에서 회수하면 제한 내용이 payload·subject·provider log에 없고 generic metadata-only 또는 `suppressed/license_restricted`로 수렴한다.
7. Resend contract는 missing/partial config, invalid key/domain, request-rate 429, daily/monthly quota, timeout-after-accept, signed/invalid/replayed webhook, duplicate `svix-id`, out-of-order event, cross-workspace provider id, bounce·complaint·suppression을 검증한다. stale Svix timestamp는 거절하고 old `created_at`+fresh valid signature replay는 처리한다.
8. 동시 reservation에서도 optional email이 account/security 최소 25건/일·750건/월을 침범하지 않는다. provider usage header와 local accepted/outstanding 값을 보수적으로 합치고 uncertain accept reservation을 조기 반환하지 않는다.
9. 비로그인 account email의 주소·device/session·IP prefix와 분리된 untrusted/proof-verified/authenticated budget을 검증하고 등록 여부·허용·제한 응답이 계정 존재를 드러내지 않는다. magic link와 manual code는 만료·lockout·동시 성공·replay·request/auth epoch·목적·return-route 격리에서 session 최대 하나다.
10. RFC 8058 GET은 해지하지 않고 urlencoded/multipart POST는 즉시·idempotent하게 해지한다. 두 형식은 정확한 one-click field 하나만 허용하고 file·추가/중복/nested part를 거절한다. active consent lineage의 오래된 token과 같은-scope replay는 opt-out을 유지하고, re-opt-in한 새 lineage와 cross-workspace/topic/channel 변조는 상태를 바꾸지 않는다. unique invalid-token flood에서도 고정-cardinality counter와 시간당 20개 reservoir 상한을 넘지 않는다. 어느 경우에도 URL·app log·referrer·audit에 token이나 digest가 없고 financial alert 해지는 account mail과 인앱 기록을 바꾸지 않는다.
11. Quiet Hours의 DST·timezone 변경, out-of-order observation, supersede와 종료 직전 TTL 만료를 고정 clock으로 검증한다. 오래된 occurrence나 만료 alert를 늦게 보내지 않는다.
12. Mailpit integration은 외부 egress와 Resend credential 없이 감사된 exact template, unsubscribe link, tracking 비활성, duplicate 0과 SMTP failure convergence를 검증한다.
